# INFO

## Что это за проект

`ystuty-schedule-bot` - это NestJS-сервис бота с расписанием для экосистемы YSTUty.
Сервис работает как бот для мессенджеров и сейчас поддерживает два канала:

- `Telegram`
- `VK`

Бот не хранит расписание у себя как источник истины. Он использует внешние сервисы YSTUty:

- `Schedule API` для списка групп, преподавателей и расписания
- `social-connect` для привязки соцпрофиля к аккаунту YSTUty
- `OAuth`-контур для получения и обновления токенов

Проект похож по структуре на другие боты в экосистеме. Часть модулей, названий компонентов и паттернов повторяется между сервисами. Поэтому этот файл нужен как краткая карта проект, чтобы быстрее понимать, что здесь можно переносить из sibling-проектов, а что завязано именно на расписание.

## Основная идея

Сервис принимает апдейты из мессенджеров, определяет пользователя и контекст диалога, получает или обновляет нужные данные и отвечает через соответствующий транспорт.

Основные сценарии:

- выбор учебной группы
- просмотр расписания на день и неделю
- выбор преподавателя
- работа в ЛС и частично в групповых чатах
- привязка мессенджер-профиля к аккаунту YSTUty через `social-connect`

## Быстрый вход в проект

Если нужно быстро понять проект, обычно достаточно идти в таком порядке:

1. `src/models/app/app.module.ts` - карта основных модулей.
2. `src/models/telegram` и `src/models/vk` - входные точки по мессенджерам.
3. `src/models/user` - пользователи, соцпрофили, привязка аккаунта.
4. `src/models/ystuty` - работа с данными расписания.
5. `src/models/social-connect` - интеграция с сервисом авторизации связки аккаунтов.
6. `src/common` - общие декораторы, фильтры, guards, util-функции.

## Карта модулей

### `src/models/app`

Корневой слой приложения.

- собирает все модули в `AppModule`
- поднимает глобальный `RolesGuard`
- логирует состояние мессенджерных сервисов
- отслеживает изменение версии приложения

### `src/models/telegram`

Адаптер Telegram на базе `@xtcry/nestjs-telegraf` + `telegraf`.

- `telegram.module.ts` - регистрация бота и middleware-цепочки
- `telegram.service.ts` - отправка сообщений, запуск бота, работа с сессией
- `update/*` - слушатели команд, callback и действий
- `scene/*` - сценарии, где нужен пошаговый диалог
- `middleware/*` - подготовка контекста, метрики, загрузка пользователя
- `telegram-keyboard.factory.ts` - генерация клавиатур

### `src/models/vk`

Адаптер VK на базе `nestjs-vk` + `vk-io`.

- `vk.module.ts` - регистрация VK API и middleware
- `vk.service.ts` - отправка/редактирование сообщений, запуск polling, сессии
- `update/*` - обработчики событий и сообщений
- `scene/*` - сценарии выбора группы и авторизации
- `middleware/*` - подготовка контекста и данных разговора
- `vk-keyboard.factory.ts` - генерация клавиатур

### `src/models/user`

Общий доменный слой пользователей.

- `User` - сущность пользователя YSTUty
- `UserSocial` - привязка пользователя к конкретной соцсети и ID внутри нее
- `user.service.ts` - создание, поиск, привязка/отвязка, завершение auth-потока

Это один из самых важных модулей при переносе логики из похожих ботов.

### `src/models/social`

Слой социальных диалогов и чатов.

- `Conversation` - сущность диалога/беседы
- `UserToConversation` - связь пользователей с беседами
- `social.service.ts` - создание и обновление бесед, добавление пользователей, хранение выбранной группы для беседы

### `src/models/social-connect`

Интеграция с внешним сервисом `social-connect`.

- делает запрос на запуск авторизации
- периодически проверяет завершение авторизации
- после подтверждения делегирует завершение привязки в `UserService`

### `src/models/ystuty` (schedule-service)

Слой работы с данными расписания.

- загружает список групп и преподавателей
- кэширует эти данные в памяти процесса
- умеет парсить название группы из текста
- получает расписание и форматирует данные для использования в update-слоях

### `src/models/redis`

Обертка над `ioredis` и `redlock`.

- хранение сессий
- блокировки на критических участках
- общая точка подключения Redis

### `src/models/metrics`

Метрики на базе Prometheus.

- счетчики пользователей и диалогов
- счетчики запросов Telegram/VK
- push в Pushgateway при включенной конфигурации

### `src/common`

Повторно используемый общий слой.

- `decorator` - метаданные для ролей, hears и ограничений
- `filter` - exception filters для HTTP, Telegram и VK
- `guard` - доступ по ролям и правам
- `util` - текстовые, oauth, i18n, menu и прочие utility-функции
- `constants`, `exception`, `pipe` - служебные общие части

### `src/interface`

Типы и интерфейсы для приложения, Telegram, VK, OAuth и расписания.

## Внешние зависимости и инфраструктура

Проект зависит от следующих внешних частей:

- `PostgreSQL` - хранение сущностей TypeORM
- `Redis` - сессии, блокировки, служебное состояние
- `Schedule API` - источник данных по расписанию
- `social-connect` - связывание соцпрофиля и аккаунта YSTUty
- `OAuth` - контур авторизации
- `Prometheus Pushgateway` - опционально для метрик

Ключевые env-группы находятся в `src/environment/index.ts`:

- приложение и порт
- PostgreSQL
- Redis
- Telegram
- VK
- OAuth / social-connect
- метрики

## Что в проекте общее с похожими ботами

С высокой вероятностью между похожими сервисами будут совпадать или частично совпадать:

- структура модулей `app`, `telegram`, `vk`, `user`, `social`, `metrics`, `redis`
- middleware-цепочки
- filters и guards
- работа с `User` / `UserSocial`
- auth-поток через `social-connect`
- часть keyboard factories
- типы `IContext`, session state, `emulateSession`
- обработка ролей, silent skip, allowed chat types
- метрики и логика базовых счетчиков

Обычно именно эти куски надо сравнивать в первую очередь при переносе обновлений из sibling-проекта.

## Что специфично именно для этого сервиса

Не все различия между проектами являются ошибками. Для этого сервиса нормальны отличия в:

- слушателях расписания
- текстах и локалях, связанных с выбором группы/преподавателя
- клавиатурах расписания
- логике парсинга групп и преподавателей
- местах, где используются сущности `Conversation` и выбранная группа чата

Если другой проект содержит дополнительный мессенджер, это не значит, что его код можно перенести сюда напрямую без адаптации. Например, модуль для мессенджера `max` пока развивается в sibling-проекте и сюда еще не интегрирован.

## Как безопасно работать с проектом

При переносе кусков из других сервисов обычно стоит проверять такой список:

1. Совпадают ли версии пакетов и не тянет ли перенос зависимость на другой API.
2. Совпадают ли типы `IContext`, session state и middleware-порядок.
3. Не завязан ли код на другой мессенджер или на другой набор env-переменных.
4. Совпадает ли логика `UserService`, `SocialConnectService`, `TelegramService`, `VkService`.
5. Не отличается ли намеренно структура слушателей и сцен.
6. Нет ли различий в сущностях и полях TypeORM.
7. Не изменились ли guards, filters и правила silent skip.

## Чувствительные зоны

При изменениях в этих местах легко получить скрытые регрессии:

- `src/common/guard/*`
- `src/common/filter/*`
- `src/models/*/middleware/*`
- `src/models/user/user.service.ts`
- `src/models/social-connect/social-connect.service.ts`
- `src/models/telegram/telegram.service.ts`
- `src/models/vk/vk.service.ts`
- session keys и `emulateSession`
- keyboard factories
- env-конфигурация и package versions

## Текущее состояние проекта
